# ad9361

**The family.** Radios whose AD9361 (or AD9363, AD9364) runs under the
Linux ad9361 driver on a Zynq, with iiod serving the IIO devices
`ad9361-phy`, `cf-ad9361-lpc` and `cf-ad9361-dds-core-lpc`. Every image
states the same attributes; the images differ in how the FPGA packs the
samples. A radio that drives the chip through its own support package, with
its own FPGA and driver, is another family.

**ADI reference images.** The ADALM-Pluto and the ADI evaluation designs
pack in libiio's channel order: 16-bit lanes from bit 0, I then Q, channel
by channel. The Pluto carries an AD9363: 325 MHz to 3.8 GHz and 20 MHz of
analog bandwidth as shipped, one receive channel, iiod over USB or over
USB gadget Ethernet at 192.168.2.1. Its context states `hw_model`.

**The cores' status flags.** The status register of each data device sits
at 0x80000088 through libiio's direct register access, which iiod serves.
On `cf-ad9361-lpc` bit 2 latches a receive overflow; on
`cf-ad9361-dds-core-lpc` bit 0 latches a transmit underflow. Writing a bit
back clears it, and a flag left from an earlier stream stays latched. The
transmit flag sets whenever the DAC holds no samples: idle, after a buffer
is created, during a buffer's first push, and once the last has played. A
Pluto showed it set after the first push of every burst and clear after
the later pushes.

**Transmit.** The DAC takes the top 12 bits of each 16-bit lane, full
scale 32767. Without a buffer the DAC core plays its tone generators, the
`altvoltage` channels of `cf-ad9361-dds-core-lpc`, at their `scale`. The
transmit LO powers down through `powerdown` on `ad9361-phy`'s output
`altvoltage1`. `hardwaregain` on the transmit channel is the attenuation,
-89.75 to 0 dB in 0.25 dB steps. libiio's kernel queue holds four buffers,
and freeing the buffer drops what it still holds.

**One clock.** Receive and transmit share the sample clock, so a rate
written for one direction is the other's too, and the blocks refuse a
second block's different rate while one block holds the radio.
`ad9361_set_bb_rate` recalibrates the radio even at the rate it already
runs, which stalled a receive stream on a Pluto for about 0.7 s. A rate is
written as whole hertz, one outside the range at the nearer end and one
that is not a number at the floor, and a request moved by more than half a
hertz is named on standard error.

**Refused tunes.** A start whose frequency lies outside the coverage, or
whose tune the radio refuses, fails, on the source as on the sink; in the
running stream such a request leaves the LO where it is. Before the first
tune of a start the setting keeps the request and the source forwards no
frequency tag, so a reset and a second start are refused again.

**Links.** libiio's USB backend claims the radio's interface for one
context, so a second context in the same process is refused; the blocks
share one context per radio for that reason, keyed by the radio's full URI
and joined by its `hw_serial`. A Pluto states `hw_serial`. iiod over the
network serves several. A Pluto's USB gadget Ethernet carried about 5
MS/s of receive and its USB backend about 7.2 MS/s; receive and transmit
at 2.5 MS/s each underran the network link.

**libiio 1.0.** libiio 1.0 renames most calls, installs `iio/iio.h` in
place of `iio.h`, and replaces the buffer with blocks that a program
enqueues and dequeues itself. A 1.0 client streams both ways from a Pluto
whose iiod is 0.26. An enqueue returns before its block reaches the radio,
where 0.x's push returns after, so the first blocks of a transmit stream
are still on the way while the program goes on. libad9361's main branch
needs libiio 1.0 and its `libad9361-iio-v0` branch 0.x; the two install the
same `ad9361.h` and the same soname, `libad9361.so.0`, and only the
library's dependency, `libiio.so.1` or `libiio.so.0`, tells them apart. The
loader picks either build by that soname alone, so a program built against
one can load the other through the library path and call a libiio it was
not built for.

**RWT radios.** Red Wire Technologies builds AD9361 radios on Zynq
UltraScale+ modules. The Oxygen has two receive and two transmit channels
from 70 MHz to 6 GHz, a GPS receiver and two USB-C ports, and serves iiod
over USB gadget Ethernet. An AD9364 build has one channel each way. The
receive ports take at most 2.5 dBm peak.

**The RWT FPGA image.** The radio loads an FPGA image and a device-tree
overlay (a "personality") before the IIO devices exist; `fpgaloader switch
default` on the radio loads the default one. Without it the context holds
no `cf-ad9361-lpc`.

**The RWT sample word.** 64-bit little-endian words of four 16-bit lanes.
One channel: two samples a word, the earlier in bits 63:32, each I high
and Q low. Two channels: the first channel in bits 31:0, the second in
63:32. The receive lanes are 12-bit samples sign-extended; the transmit
lanes are left-justified, full scale 32767.

**RWT in-band tags.** A word equal to the escape value (reset value
0xAAAAAAAAAAAAAAAA) starts a tag; an escape and a zero word stand for a
sample word equal to the escape. A tag word holds a continue flag in bit
63, the type in 62:56 and the value in 55:0. Receive sends PPS (2) and
overflow (3), each with the sample index of the next word; transmit takes
hold (4), start of burst (5) and end of burst (6). The receive path inserts
tags only after its control register enables them; its reset value leaves
them off.

**RWT registers.** The RWT FPGA's own registers (escape value, tag
enables, sample-index counter, CIC decimator) sit at physical address
0x9D000000 on the radio and are reached through `/dev/mem` there. iiod
does not serve them, so a host reads none of them. The CIC decimates by
powers of ten for rates under 600 kS/s; a host cannot set it, and a radio
left decimating by an earlier on-radio run delivers a rate the host did
not ask for.

**Rates.** The AD9361 runs to 61.44 MS/s. Under 25e6/12 S/s its FIR must
decimate; libad9361's `ad9361_set_bb_rate` designs that filter and reaches
25e6/48 S/s.
